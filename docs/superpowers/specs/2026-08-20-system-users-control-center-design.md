# مركز تحكم المستخدمين الآليين

## الهدف والنطاق

تطوير تبويب **الإعدادات ← مستخدمو النظام** إلى مركز تحكم آمن لإدارة المستخدمين الآليين. يتيح للمدير تعريف سلوك كل مستخدم آلي، ومعرفته، وحضوره، ومراسلاته، ومصادر البيانات التي يستطيع قراءتها.

يبقى نطاق المراسلات داخل النظام فقط. لا يضيف هذا العمل إرسالًا عبر واتساب أو SMS أو البريد الإلكتروني.

## الواجهة

تحتفظ الصفحة بالتحكم العام في تفعيل المحاكاة وتشغيلها، وتضيف ملخصًا لحالة كل مستخدم آلي: التفعيل، التعليمات، الحضور، نافذة الرد، ومصادر البيانات.

يُختار مستخدم آلي من قائمة موجزة، وتظهر إعداداته في أقسام منفصلة:

1. **التشغيل والهوية:** الحالة الحالية وإعدادات المحاكاة الموجودة.
2. **التوجيهات والمعرفة:** تعليمات خاصة بالمستخدم، وتعليمات عامة مشتركة، ومقالات قاعدة المعرفة.
3. **الحضور والانصراف:** الوردية وأيام العمل، نسب العشوائية، وتوليد السجلات التاريخية.
4. **المراسلات:** أسلوب الرد، سرعة الرد، أوقات وأيام الرد، وأنواع الرسائل المسموح بها.
5. **مصادر البيانات:** مصادر جاهزة حسب المجال، واختيار متقدم لجداول قراءة مسموحة.
6. **النشاط:** آخر التغييرات ونتائج التشغيل.

إعادة تنظيم الصفحة من البطاقات المسطحة الحالية إلى قائمة مستخدمين ومساحة إعدادات مقسمة جزء صريح من نطاق العمل.

## التعليمات وقاعدة المعرفة

تُنقل واجهة إدارة قاعدة المعرفة الحالية من مركز خدمة العملاء إلى تبويب مستخدمي النظام، مع الاحتفاظ بالمقالات الموجودة وعدم حذف البيانات.

يقدم النظام طبقتين:

- تعليمات ومقالات عامة مشتركة لكل المستخدمين الآليين.
- تعليمات ومقالات خاصة بمستخدم آلي محدد، تضاف فوق المحتوى العام.

يحتوي كل عنصر على عنوان، محتوى، فئة، أولوية، حالة نشر، ونوع:

- `knowledge`: معلومة مرجعية.
- `instruction`: توجيه أسلوبي أو تشغيلي.
- `command`: قاعدة عمل ملزمة ضمن قدرات المستخدم المسموحة.

تُقرأ العناصر العامة المنشورة أولًا ثم عناصر المستخدم الخاصة، مرتبة بالأولوية، عند بناء سياق المستخدم الآلي. لا تُدمج هذه البيانات مع `modern_agent_knowledge`.

### ترحيل قاعدة المعرفة الحالية

تظل بيانات المقالات الحالية في جدول `customer_service_knowledge`، وتضاف إليه:

- `system_user_id integer null`: القيمة الفارغة تعني عنصرًا عامًا، والقيمة المحددة تعني عنصرًا خاصًا بذلك المستخدم الآلي.
- `item_type varchar(20) not null default 'knowledge'`.
- `priority integer not null default 100`.

تُعامل جميع الصفوف الحالية تلقائيًا كمعرفة عامة منشورة بأولوية 100. تُزال واجهة المعرفة من صفحة خدمة العملاء، وتنتقل الإدارة إلى `/api/system-users/knowledge`.

تُوقف مسارات الكتابة القديمة `POST/PUT/DELETE /api/customer-service/knowledge` حتى لا تتجاوز صلاحيات مركز التحكم، بينما يبقى `GET` للقراءة المتوافقة مؤقتًا. لا يُحذف الجدول ولا أي مقال قائم.

## الحضور والانصراف

تبقى إعدادات الوردية، أيام العمل، احتمال الغياب، احتمال التأخير وحده الأقصى، واحتمال الخروج المبكر وحده الأقصى هي مصدر العشوائية اليومي.

يُضاف تاريخ بداية اختياري للمستخدم الآلي. لا ينشئ المحاكي حضورًا قبل هذا التاريخ.

يستطيع المدير اختيار تاريخ بداية سابق وتاريخ نهاية ثم معاينة عدد الأيام المؤهلة، الأيام التي ستنشأ، الأيام الموجودة، وأيام الغياب المحاكاة. يؤكد المدير الإنشاء قبل كتابة أي سجل. لا يستبدل النظام أو يكرر أي سجل موجود للمستخدم في اليوم نفسه.

تُنشأ سجلات فعلية في جدول `attendance` بالحالة `حاضر` وملاحظة `مستخدم نظام (محاكاة تاريخية)`. يكون `created_by` هو المدير المنفذ. يستخدم التشغيل اليومي الحالي الملاحظة الحالية `مستخدم نظام (محاكاة)`.

## المراسلات داخل النظام

تحدد إعدادات كل مستخدم آلي:

- أسلوب الرد: مهني، مختصر، تفصيلي، أو مخصص.
- تعليمات رد إضافية.
- حد أدنى وأعلى لتأخير الرد.
- أيام وساعات السماح بالرد.
- فئات الرسائل المسموح التعامل معها.
- الهدف والحد اليومي للرسائل الاستباقية الموجودان حاليًا.

عند وصول رسالة، ينشئ المحاكي قرار رد ثابتًا في طابور الردود. يحسب وقت التنفيذ مرة واحدة من الحدين الأدنى والأعلى، وينقله إلى أول نافذة مسموحة إذا وقع خارجها. يحفظ الطابور القرار عبر إعادة تشغيل الخادم ويمنع جدولة ردين للرسالة نفسها.

تبقى حراسة حلقات الرسائل بين المستخدمين الآليين والحد اليومي الحاليان فعالين. تُسجل نتيجة التأجيل أو الإرسال أو التجاوز دون تخزين نص الرسالة كاملًا في سجل النشاط.

## مصادر البيانات والجداول

تمنح الصفحة وصول قراءة فقط بطبقتين:

- مصادر جاهزة مفهومة حسب المجال.
- قائمة جداول متقدمة متاحة لمدير يملك صلاحية `admin`.

لا تقبل الواجهة أو الخادم استعلامات SQL حرة. لا تُنفذ أسماء الجداول القادمة من الطلب مباشرة. يبني الخادم الاستعلام من سجل ثابت للمصادر والجداول والحقول الآمنة.

### المصادر الجاهزة

| المفتاح | المجال | الجداول والحقول الآمنة |
|---|---|---|
| `customers` | العملاء | `customers`: `name`, `name_ar`, `city`, `is_active` |
| `products` | منتجات العملاء | `customer_products`: `size_caption`, `raw_material`, `status` |
| `orders` | الطلبات | `orders`: `order_number`, `status`, `delivery_date`, `created_at` مع اسم العميل فقط |
| `production` | الإنتاج | `production_orders`: رقم أمر الإنتاج، الكميات، ونسب اكتمال المراحل؛ و`machines`: الاسم، النوع، والحالة |
| `attendance` | الحضور | `attendance`: المستخدم، التاريخ، الحالة، أوقات الدخول والخروج والاستراحة، ساعات العمل، الوردية، التأخير، والخروج المبكر |
| `messages` | المراسلات | `internal_messages`: الموضوع، المحتوى، الفئة، والتواريخ للرسائل التي يكون المستخدم الآلي مرسلها أو مستلمها فقط |
| `reports` | الملخصات | إجماليات مشتقة من المصادر المصرح بها فقط، دون جدول مستقل |

يستبعد مصدر الحضور بيانات الجهاز والموقع والملاحظات. ويستبعد مصدر العملاء الهاتف والعنوان والرقم الضريبي والتجاري والمعرفات الحساسة.

### الجداول المتقدمة

تقتصر القائمة على:

- `customers`
- `customer_products`
- `orders`
- `production_orders`
- `machines`
- `attendance`
- `internal_messages`

حتى عند اختيار جدول متقدم تبقى قيود الحقول والصفوف أعلاه سارية. اختيار الجدول لا يعني كشف كل أعمدته.

## نماذج البيانات

### توسيع `system_user_settings`

تُضاف الحقول التالية، وتبقى الحقول الحالية دون تغيير:

- `attendance_start_date date null`.
- `reply_style varchar(20) not null default 'professional'` بقيم `professional | concise | detailed | custom`.
- `reply_instructions text null` بحد 4000 حرف.
- `reply_delay_min_minutes integer not null default 0`.
- `reply_delay_max_minutes integer not null default 0`.
- `reply_allowed_days text null` كمصفوفة JSON؛ القيمة الفارغة تستخدم `allowed_days`.
- `reply_window_start varchar(5) null` و`reply_window_end varchar(5) null` بصيغة `HH:mm`؛ القيم الفارغة تستخدم نافذة الوردية الحالية.
- `allowed_message_categories text not null` كمصفوفة JSON، وافتراضيًا تشمل: `عامة`, `تكليف عمل`, `إشعار خصم`, `إنذار`, `توكيل مهام`.

تتحقق المخططات من أن الحد الأدنى للتأخير لا يتجاوز الحد الأعلى، وأن الأوقات والقيم صحيحة. تحافظ القيم الافتراضية على سلوك المستخدمين الحاليين. يبقى `persona` وصف الهوية والدور ولا يتحول تلقائيًا إلى مقال معرفة.

### `system_user_data_access`

- `id serial primary key`
- `user_id integer not null`
- `access_kind varchar(10) not null`: `source` أو `table`
- `access_key varchar(100) not null`
- `created_by integer null`
- `created_at timestamp`
- قيد فريد على `(user_id, access_kind, access_key)`

يجب أن يرتبط `user_id` بمستخدم يحمل `is_system_user = true`. لا تُستخدم قيمة `access_key` كنص SQL، بل تطابق مفتاحًا في السجل الثابت للخادم.

### `system_user_activity`

- `id serial primary key`
- `system_user_id integer null`
- `actor_id integer null`
- `action varchar(50) not null`
- `details jsonb not null default '{}'`
- `created_at timestamp`

تشمل الإجراءات تحديث الإعدادات، إدارة المعرفة، تغيير وصول البيانات، معاينة أو إنشاء الحضور، قرارات الرسائل، وتشغيل المحاكاة. لا تحتوي `details` على أسرار أو نصوص رسائل كاملة.

### `system_user_message_queue`

- `id serial primary key`
- `system_user_id integer not null`
- `incoming_message_id integer not null unique`
- `scheduled_at timestamp not null`
- `status varchar(20) not null`: `pending | sent | skipped`
- `reason varchar(100) null`
- `response_message_id integer null`
- `processed_at timestamp null`
- `created_at timestamp`

يمنع القيد الفريد جدولة أكثر من رد للرسالة نفسها.

## الواجهات الخلفية

تستمر المسارات الحالية `GET /api/system-users` و`PUT /api/system-users/:userId/settings` ومسارات تشغيل المحاكاة. تصبح الحقول الجديدة اختيارية في طلب التحديث وتُعاد ضمن `settings`.

تضاف:

- `GET /api/system-users/knowledge?system_user_id=&item_type=&search=`
- `POST /api/system-users/knowledge`
- `PUT /api/system-users/knowledge/:id`
- `DELETE /api/system-users/knowledge/:id`
- `GET /api/system-users/:userId/data-access`
- `PUT /api/system-users/:userId/data-access`: يستبدل قائمتي المصادر والجداول ذريًا بعد رفض أي مفتاح غير معرف.
- `POST /api/system-users/:userId/attendance/history/preview`
- `POST /api/system-users/:userId/attendance/history/generate`
- `GET /api/system-users/:userId/activity?limit=&cursor=`

### عقد الحضور التاريخي

يستقبل مسارا المعاينة والإنشاء:

```json
{ "start_date": "YYYY-MM-DD", "end_date": "YYYY-MM-DD" }
```

يكون `end_date` افتراضيًا أمس، وبحد أقصى 366 يومًا في العملية الواحدة. تعيد المعاينة دون كتابة:

```json
{
  "eligible_days": 0,
  "would_create": 0,
  "existing_days": 0,
  "simulated_absent_days": 0
}
```

يعيد الإنشاء:

```json
{
  "created": 0,
  "skipped_existing": 0,
  "absent": 0,
  "start_date": "YYYY-MM-DD",
  "end_date": "YYYY-MM-DD"
}
```

يقفل الخادم عملية التوليد على المستخدم الآلي. إذا وُجد أي سجل حضور له في يوم معين، يتجاوز اليوم بالكامل دون تعديل.

## دمج المحاكي

يبني المحاكي سياق كل مستخدم من:

1. الهوية `persona`.
2. المعرفة العامة المنشورة.
3. المعرفة الخاصة المنشورة.
4. عينات البيانات من المصادر والجداول الممنوحة فقط.

تُعامل التعليمات التي أنشأها المدير كسياق موثوق. تظل الرسائل الواردة وقيم جداول الأعمال بيانات غير موثوقة، ولا يجوز تنفيذ أوامر واردة داخلها.

يفحص معالج الرد فئة الرسالة وأيام وساعات الرد قبل الجدولة. يعالج طابور الردود عند حلول `scheduled_at` ويحترم الحد اليومي وحارس الحلقات.

لا يمنح الترحيل أي مصدر جديد تلقائيًا، باستثناء منح `customers`, `products`, و`orders` للمستخدمين الحاليين فقط للحفاظ على سياق الرسائل القائم. لا يُنشأ حضور تاريخي تلقائيًا.

لا توجد قرارات رد معلقة محفوظة قبل الترحيل؛ بعده يلتقط المحاكي الرسائل غير المقروءة القائمة ويجدولها مرة واحدة في الطابور الجديد، لذلك لا تسقط الرسائل الواردة السابقة.

## الصلاحيات وسجل التدقيق

تظل رؤية الصفحة وتعديل الإعدادات العادية متاحة وفق صلاحيات التبويب الحالية: `manage_users` أو `manage_settings` أو `manage_definitions` أو `admin`.

يقتصر منح الجداول المتقدمة وإنشاء الحضور التاريخي على من يملك `permissions.includes("admin")` صراحة؛ لا يعتمد ذلك على رقم الدور. يتحقق الخادم من الصلاحيات ولا يعتمد على إخفاء عناصر الواجهة.

يسجل النظام المنفذ، المستخدم الآلي المستهدف، القيم السابقة والجديدة للإعدادات، ونتيجة العمليات الحساسة. تُكتب التغييرات وسجل النشاط في معاملة واحدة عند تعديل الإعدادات أو الوصول أو المعرفة.

## تبويب النشاط

يعرض آخر 100 حدث للمستخدم الآلي المختار بترتيب الأحدث، مع نوع الحدث، وقته، المنفذ، وملخص آمن للنتيجة. يدعم تحميل الصفحة التالية بالمؤشر. مصدره الوحيد `system_user_activity`.

لا يعرض نصوص الرسائل كاملة أو محتوى التعليمات المحذوفة.

## حالات الفشل

- يرفض توليد الحضور إن كان التاريخ غير صالح أو لم تضبط الوردية.
- يتجاوز السجلات الموجودة ويعرض عددها بدل تعديلها.
- يرفض نطاقًا يتجاوز 366 يومًا؛ يمكن تنفيذ نطاقات متتالية لتاريخ أطول.
- يرفض مصدرًا أو جدولًا أو فئة رسالة غير معرفة.
- يؤجل الرد خارج الوقت المسموح ويسجل القرار مرة واحدة.
- يعرض أخطاء الحفظ بوضوح ولا يحدّث الواجهة بتغيير غير محفوظ.
- إذا فشل توليد النص، يستخدم المحاكي الرد القالبي الحالي دون تجاوز نافذة الرد أو صلاحيات البيانات.

## التحقق

- اختبار حفظ وعرض التعليمات العامة والخاصة وترتيب الأولوية.
- اختبار إزالة واجهة المعرفة من مركز خدمة العملاء مع بقاء المقالات.
- اختبار توليد سجلات تاريخية عشوائية ضمن الحدود ومنع التكرار.
- اختبار صلاحية `admin` لتوليد التاريخ ومنح الجداول المتقدمة.
- اختبار منع الرد خارج ساعات العمل والفئات غير المسموحة.
- اختبار ثبات وقت الرد المجدول عبر إعادة تشغيل المحاكي ومنع تكراره.
- اختبار رفض إعداد تكون فيه قيمة `reply_delay_min_minutes` أكبر من `reply_delay_max_minutes`.
- اختبار رفض أي مصدر أو جدول غير مصرح به في الخادم.
- اختبار بقاء قيود الحقول والصفوف عند اختيار جدول متقدم.
- اختبار كتابة التغييرات وسجل التدقيق ذريًا.
- التحقق من TypeScript، فحص حجم الملفات، وسلامة تشغيل التطبيق.
